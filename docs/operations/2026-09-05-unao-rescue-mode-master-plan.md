상태: **ACTIVE - Rescue 운영 전략 정본**
적용 대상: 우리 나이가 어때서(age-doesnt-matter.com)

## 0. 이 문서의 목적

이 문서는 우나어를 다시 살리기 위한 Rescue Mode의 기준이다.

새 기능 구현 계획서가 아니다. 리팩토링 목록도 아니다. Claude에게 일을 많이 시키기 위한 프롬프트도 아니다.

목적은 하나다.

> 우나어를 네이버와 사용자에게 다시 신뢰받는 커뮤니티로 소생시킨다.

코드 정리, 인프라 정리, 문서 정리, 자동화 제거, 주석 수정, 콘텐츠 정리는 전부 이 목적의 수단이다.
이 목적에 직접 기여하지 않는 작업은 긴급해 보여도 뒤로 보낸다.

### 문서 역할과 위계

**이 문서가 최상위 운영 정본이다.** 창업자가 승인한 Rescue 마스터플랜이며, 전략·마일스톤·금지선·
완료 기준을 정의한다. 매일 바뀌는 진행률과 다음 작업은 이 문서에 누적하지 않고
`UNAO_RESCUE_STATUS.md`에서 관리한다.

1. **이 문서** — 최상위 운영 정본. Rescue 전략, 마일스톤, 금지선과 완료 기준
2. `UNAO_RESCUE_STATUS.md` — 현재 판정, 완료 증거, 열린 위험과 다음 게이트
3. 범위별 정책 문서 · `OPERATING_BACKLOG.md` · ops-board ledger — 승인된 세부 작업
4. reports / handoff — 조사 증거와 과거 기록. 현재 우선순위를 결정하지 않는다

하위 문서는 상위 문서를 덮어쓸 수 없다. 충돌하면 작업을 멈추고 Codex가 재판정한다.

### `docs/constitution/NORTH_STAR.md`의 현재 지위

**초기 전략 문서다.** 서비스가 왜 존재하는지에 대한 배경으로 읽되, **레거시 재감사가 끝나기
전까지 구현 명령의 근거로 사용하지 않는다.** 그 문서의 지표 정의·KPI·목표 수치를 인용해
코드 변경, DB 컬럼 추가, 대시보드 구현을 정당화하지 않는다. 구현 근거는 항상 이 문서와 상태판이다.

## 1. 우나어의 본질

우나어는 일자리 플랫폼이 아니다.
크롤러 사이트가 아니다.
봇 자동화 실험장이 아니다.
SEO 트래픽 수집기가 아니다.

우나어의 본질은 다음 한 문장이다.

> 40대 중반~60대 중반 여성이 "나만 이런 게 아니구나"를 확인하고, 다시 찾아와 글이나 댓글을 남기는 커뮤니티.

일자리, 매거진, SEO, 크롤러, 에이전트, 광고, 알림, 운영 대시보드는 모두 수단이다.
수단이 본질을 흐리면 제거하거나 축소한다.

---

## 2. 현재 생존 가설

우나어는 완전히 죽었다고 단정하지 않는다.
다만 지금은 생존 신호가 약하고, 네이버 신뢰와 운영 신뢰가 흔들린 상태로 본다.

따라서 현재 판정은 다음과 같다.

| 영역 | 판정 | 의미 |
|---|---|---|
| 서비스 본질 | 유지 | 커뮤니티 본질은 아직 유효하다 |
| 네이버 신뢰 | 위험 | 복사글, 저품질 자동글, URL 오염 가능성을 정리해야 한다 |
| 로그인/참여 | P0 | 로그인 문제가 있으면 커뮤니티 회복이 불가능하다 |
| 콘텐츠 공급 | 위험 | 외부 크롤 기반 글은 전면 재판정이 필요하다 |
| 자동화 | 위험 | ACTIVE 문서가 실제 가치와 일치하는지 검증해야 한다 |
| 문서 체계 | 위험 | 오래된 문서가 목적과 실행을 오도하고 있다 |
| 코드/인프라 | 위험 | 하드코딩, 레거시, 중복 경로, 잘못된 주석을 정리해야 한다 |

## 3. 마스터의 역할

Codex 마스터는 구현자가 아니라 운영 지휘자다.
Claude가 손과 발이면, Codex 마스터는 목적, 순서, 금지선, 검증 기준을 책임진다.

### 책임

1. 목적을 고정한다.
   - 모든 작업을 "우나어 소생에 기여하는가"로 판단한다.
   - 코드 청소 자체를 목표로 삼지 않는다.

2. 문제를 정의한다.
   - 로그인, 네이버 신뢰, 콘텐츠 오염, 자동화 사망, 문서 오염, 인프라 혼선을 분리해서 본다.
   - 증상 패치보다 원인과 재발 방지 기준을 먼저 잡는다.

3. Claude를 지휘한다.
   - read-only 조사, 수정 허용 범위, 금지사항, 산출물 형식, PASS 기준을 명확히 준다.
   - 큰 작업을 한 번에 시키지 않고 PR 단위로 자른다.

4. Claude 보고를 검증한다.
   - "완료" 보고를 그대로 믿지 않는다.
   - diff, 테스트, 런타임, 운영 데이터, SEO 영향, DB 위험을 다시 판정한다.

5. 창업자의 판단 피로를 줄인다.
   - 지금 할 것, 하면 안 되는 것, Claude에게 시킬 것, 나중에 할 것을 분리한다.

6. 우나어와 소란소란을 분리한다.
   - 소란소란은 별도 서비스, 별도 repo, 별도 DB, 별도 인프라다.
   - 우나어 Rescue 작업 중 소란소란 코드를 섞지 않는다.

### 하지 않는 일

- Claude처럼 무작정 구현부터 하지 않는다.
- Claude 보고를 중계만 하지 않는다.
- 로그인, SEO, DB, 자동화, 문서를 한 번에 흔들지 않는다.
- 네이버 신뢰가 걸린 콘텐츠를 무작정 대량 삭제하라고 하지 않는다.
- 소란소란 코드를 우나어에 직접 복사하라고 하지 않는다.

## 4. Rescue Mode 목표

### 7일 목표

1. 로그인/가입/세션 문제를 최우선으로 진단하고 복구한다.
2. 네이버 신뢰를 더 훼손하는 자동 발행/저품질 노출 경로를 식별한다.
3. 복사글, 저품질글, 얇은 글, 중복글의 판정 기준을 만든다.
4. 정본 문서와 폐기 후보 문서를 분리한다.
5. 죽은 자동화와 위험 자동화를 KEEP/OFF/REMOVE 후보로 나눈다.

### 30일 목표

1. 네이버 수집, 색인, 노출, 클릭을 분리해서 회복 여부를 관찰한다.
2. 저품질/복사 위험 콘텐츠를 noindex, 비공개, 리라이트, 삭제 후보로 처리한다.
3. 사망 판정 자동화와 목적이 뒤집힌 workflow/launchd를 제거 또는 OFF 처리한다.
4. `README.md`, `CLAUDE.md`, `AGENTS.md`, `docs/features/REGISTRY.md`, 주요 헌법 문서의 정합성을 맞춘다.
5. 도메인, absolute path, 색상, env fallback, localStorage key 하드코딩을 단계적으로 제거한다.

### 90일 목표

1. 우나어 유지, 축소 운영, 소란소란 집중 중 하나를 결정할 수 있는 운영 근거를 확보한다.
2. 실회원 글/댓글/재방문이 회복되는지 확인한다.
3. 검증된 콘텐츠 파이프라인을 우나어에 붙일지 여부를 결정한다.

### R8 커뮤니티 회복 — 관찰 방식

지금은 복합 지표를 만들지 않는다. **네 숫자를 각각 그대로 본다.**

| 관찰 대상 |
|---|
| 신규 가입 |
| 실회원 글 |
| 실회원 댓글 |
| 재방문 회원 |

- 기존 North Star 1명은 **임시 참고치**다. 개발 게이트도 확정 목표도 아니다.
- **복합 North Star 시스템 구현은 HOLD.** 계산식·표시·테스트를 새로 만들지 않는다.
- **충분한 실사용 표본이 생기기 전까지 DB 컬럼·스냅샷·그래프를 추가하지 않는다.**
- 표본이 한 자릿수인 동안 지표 정의를 정교하게 만드는 일은 회복에 기여하지 않는다.

### 5-S. 기반 단순화 / 레거시 제거 — 현재 핵심 프로그램

**새 마일스톤이 아니다.** 기존 R4·R5·R6을 하나의 목적으로 묶어 실행하는 프로그램이며,
서비스가 실제로 쓰는 것만 남기는 일이다. 남아 있는 잔재가 운영 판단을 오도하고 유지비를 만든다.

**역할 분리**

| 단계 | 이 프로그램에서 맡는 범위 |
|---|---|
| **R4 자동화 단순화** | C-level 및 역할극 에이전트 · 사용하지 않는 workflow · runner · registry · 보지 않는 Slack · 리포트 · AdminQueue 자동화 |
| **R5 문서 단순화** | 오도·중복·정지된 문서. 정본이 아닌 것을 정본처럼 쓰지 않게 한다 |
| **R6 코드·지표·연동·스크립트·의존성 단순화** | 오래된 KPI·지표·스냅샷·대시보드 · UI·디자인 도구(Figma 포함) 및 사용하지 않는 외부 연동 · 일회성 scripts·backfill · 미사용 API·패키지·환경변수·테스트 |

**유지 분류 (5종)**

| 분류 | 정의 |
|---|---|
| **KEEP_CORE** | 창업자가 승인한 핵심 제품이며 **실제 사용 증거가 있음** |
| **KEEP_SAFETY** | 보안 · 개인정보 · 데이터 정합성에 필요 |
| **KEEP_RECOVERY** | **실행 절차와 사용 조건이 문서화된** 복구 도구 |
| **REMOVE** | 위 근거가 없거나 대체 경로가 있음 |
| **FOUNDER_DECISION** | 코드와 운영 증거만으로 **사업 의도를 확정할 수 없음** |

> **route·registry·workflow에 존재한다는 사실 자체는 KEEP 근거가 아니다.**
> "언젠가 쓸 수 있음", "등록돼 있음", "코드가 남아 있음"도 근거가 아니다.
> 복구 도구는 실행 절차와 사용 조건이 문서로 있어야 KEEP_RECOVERY다. 이름만으로는 안 된다.

**완료 기준**

1. REMOVE 대상은 코드뿐 아니라 **runner · registry · workflow · env · 문서 · 테스트 · 패키지 참조까지
   dependency closure 전체가 제거**돼야 한다. 코드만 지우고 참조가 남으면 완료가 아니다.
2. **남긴 항목마다 유지 분류(KEEP_CORE / KEEP_SAFETY / KEEP_RECOVERY)와 그 근거인 운영 증거가
   기록**돼야 한다. 근거 없이 남은 항목이 하나라도 있으면 완료가 아니다.
3. FOUNDER_DECISION 항목은 창업자 판단 전까지 미결로 두되, 목록과 판단에 필요한 정보를 함께 제시한다.

제거는 되돌리기 쉬운 작은 PR로 나눈다. 삭제 전 재가동 방지선을 먼저 두고,
판정표는 창업자 승인 후 실행한다.

## 7. 콘텐츠 신뢰 정리 원칙

네이버 카페 등 외부에서 가져온 글은 전부 재판정 대상이다.
하지만 무작정 삭제하지 않는다. 삭제는 마지막 처리 방식이다.

| 콘텐츠 상태 | 처리 원칙 |
|---|---|
| 명백한 복사글 + 유입/댓글 없음 | noindex 또는 비공개 후 삭제 후보 |
| 복사 위험 있음 + 유입 있음 | 리라이트/보강 후보 |
| 사용자 댓글 또는 반응 있음 | 삭제 금지, 본문 정리 또는 보강 우선 |
| 광고/공지/차단문/빈 글 | 즉시 격리 후보 |
| 중복 주제/반복 문장 구조 | 통합, noindex, 리라이트 후보 |
| 판단 애매 | 색인 제외 후 관찰 |

삭제보다 먼저 해야 할 일:

1. 어떤 URL이 네이버에 노출되어 있는지 확인한다.
2. 어떤 글이 사용자 반응을 받았는지 확인한다.
3. 어떤 글이 원문 복사 위험이 큰지 판정한다.
4. `noindex`, sitemap 제외, 비공개, 리라이트, 삭제 중 처리 방식을 나눈다.
5. 삭제 시 404 폭증 위험을 평가한다.

## 13. 성공 기준

### 단기 PASS

- 로그인 문제가 원인별로 분리되고 복구 경로가 확정된다.
- 네이버 신뢰를 더 깎는 발행/색인 경로가 멈추거나 격리된다.
- 위험 콘텐츠 처리 기준이 생긴다.
- 죽은 자동화와 위험 자동화가 분류된다.
- Claude가 어떤 문서를 믿어야 하는지 명확해진다.

### 중기 PASS

- 네이버 수집, 색인, 노출, 클릭을 분리해서 관찰한다.
- 검색엔진에 보여줄 URL과 숨길 URL이 분리된다.
- 자동화 상태가 문서와 실제 실행 상태에서 일치한다.
- 주요 문서가 우나어 본질과 충돌하지 않는다.
- 새 콘텐츠 파이프라인을 붙일 수 있는 코드/인프라 경계가 생긴다.

### 실패 기준

- 로그인 복구 전에 대규모 리팩토링을 시작한다.
- 복사글을 대량 삭제해서 404 위험을 만든다.
- 소란소란 작업과 우나어 작업이 섞인다.
- Claude가 오래된 handoff 문서를 정본처럼 따른다.
- 자동화가 계속 저품질 콘텐츠를 발행한다.
- 문서만 정리되고 운영 위험이 줄지 않는다.

## 16. Rescue 지표판

**Rescue Mode에서는 복합 대표지표를 만들지 않는다.** 커뮤니티 회복은 신규 가입 · 실회원 글 ·
실회원 댓글 · 재방문 회원 **네 숫자를 각각 단순 관찰**한다(§5 R8).

기존 "주간 재방문 참여 유저 수"의 임시 측정값 1명은 **참고치**이며 개발 게이트도 확정 목표도 아니다.
복합 North Star 시스템 구현은 HOLD이고, 충분한 실사용 표본이 생기기 전까지
DB 컬럼·스냅샷·그래프를 추가하지 않는다.

선행 지표와 후행 지표는 아래처럼 분리해 본다.

### 선행 생존 지표

| 지표 | 왜 보는가 | PASS 방향 |
|---|---|---|
| 로그인 가능 여부 | 참여의 입구 | 카카오 로그인, 세션, 온보딩, 글/댓글 진입 정상 |
| 홈/대표 URL 200 | 사이트 생존 기본 | production URL 정상 응답 |
| `/api/health/auth` | auth/env/db 최소 상태 | ok=true |
| `/api/auth/csrf`, `/api/auth/providers` | NextAuth runtime 기본 | 200 |
| sitemap/robots/canonical | 검색 신뢰 기본 | 의도한 대표 URL만 노출 |
| 자동 발행량 | 저품질 누적 방지 | 임시 상한 이하 또는 중단 |
| 신규 저품질 URL 수 | 네이버 신뢰 방어 | 0 또는 승인된 소수 |

### 검색 회복 지표

| 지표 | 해석 |
|---|---|
| 네이버 수집 | 네이버가 다시 보러 오는지 |
| 네이버 색인 | 검색 대상 문서로 인정하는지 |
| 네이버 노출 | 검색 결과에 다시 보이는지 |
| 네이버 클릭 | 실제 유입이 회복되는지 |
| 브랜드명 검색 홈 노출 | 대표 사이트 신뢰가 돌아오는지 |

### 커뮤니티 회복 지표

각각 따로 본다. 하나로 합치지 않는다.

| 지표 | 해석 |
|---|---|
| 신규 가입 | 새 사람이 들어오는지 |
| 실회원 글 수 | 사람이 말하기 시작했는지 |
| 실회원 댓글 수 | 대화가 생기는지 |
| 재방문 회원(봇 제외) | 커뮤니티 생명력 |
| 외부글 대비 사용자 반응 | 외부글이 대화 씨앗 역할을 하는지 |

주의:

- PV, DAU, 색인 수, 크롤 수집량은 단독 목표가 아니다.
- 하지만 Rescue Mode에서는 "생존 참고지표"로 매일 본다.
- 지표가 좋아져도 실회원 참여가 없으면 소생 완료가 아니다.

## 17. Rescue 작업 레인

작업은 아래 레인으로 나눈다.
한 번에 모든 레인을 수정하지 않는다.

| 레인 | 이름 | 목적 | 쓰기 허용 시점 |
|---|---|---|---|
| L0 | Command/Sync | 목적, 금지선, 마일스톤 고정 | 즉시 |
| L1 | Login/Auth | 로그인, 세션, 온보딩, 글/댓글 진입 복구 | read-only 진단 후 |
| L2 | Naver Trust | sitemap, robots, canonical, noindex, 대표 URL | 수치 감사 후 |
| L3 | Content Trust | 복사글, 저품질글, 중복글, 얇은 글 처리 | dry-run 목록 후 |
| L4 | Automation Containment | 위험 bot/workflow/launchd 차단 | 실제 ON/OFF 대조 후 |
| L5 | Docs Constitution | 정본/오래된 문서/오도 문서 정리 | L0 확정 후 |
| L6 | Code/Infra Cleanup | 하드코딩, 주석, 레거시, config 정리 | P0 안정 후 |
| L7 | Rebuild | 새 콘텐츠 공급, 우나어식 발행 gate | R1~R6 후 |

동시 진행 제한:

- L1 로그인과 L4 자동화 관측은 병렬 가능하다.
- L2 SEO 변경과 L3 콘텐츠 처분은 병렬 수정 금지다.
- L1 로그인 복구 전에는 대규모 L6 리팩토링 금지다.
- L4에서 OFF/REMOVE 전에는 `.env.local`, `.github/workflows`, `launchd`, 실제 로그를 대조한다.

## 19. 콘텐츠 데이터룸

복사글/저품질글은 감으로 삭제하지 않는다.
먼저 데이터룸을 만든다.

필수 분류 축:

| 축 | 예시 |
|---|---|
| source | USER, ADMIN, BOT, SHEET |
| boardType | STORY, HUMOR, LIFE2, MENOPAUSE, MAGAZINE, JOB |
| sourceUrl/sourceSite | 82cook, 네이버 카페, 기타 외부 |
| content length | 300자 미만, 300~800자, 800자 이상 |
| user reaction | 실회원 댓글/좋아요/스크랩/조회 |
| search signal | 네이버/GSC 노출/클릭 여부 |
| duplication risk | 제목 유사, 본문 유사, sourceUrl 중복, 구조 반복 |
| legal/brand risk | 출처 흔적, 원문 복사, 광고/공지/차단문 |

처리 우선순위:

1. 광고/공지/차단문/빈 글
2. 명백한 복사글 + 반응 없음
3. 얇은 외부글 + 검색 신호 없음
4. 중복 주제 대량 반복
5. 복사 위험은 있으나 유입/댓글이 있는 글
6. USER/ADMIN 직접 작성 글

USER/ADMIN 글은 기본 보호한다.
외부글 정리 중 사용자 자산을 같이 죽이면 Rescue 실패다.

## 20. 콘텐츠 처분 사다리

처분은 강도가 낮은 순서로 검토한다.

| 단계 | 처리 | 의미 | 되돌리기 |
|---|---|---|---|
| 1 | 내부 관찰만 | 아직 노출 유지 | 쉬움 |
| 2 | sitemap 제외 | 제출 대상에서 제외 | 쉬움 |
| 3 | noindex, follow | 사용자는 볼 수 있고 검색 대표에서 제외 | 비교적 쉬움 |
| 4 | 비공개/숨김 | 사용자 노출 중단 | 중간 |
| 5 | 리라이트/보강 | 살릴 가치가 있는 글을 우나어식 자산으로 전환 | 중간 |
| 6 | 삭제/404 또는 410 | 문서 폐기 | 어려움 |

삭제/404/410은 마지막이다.
대량 삭제는 Search Advisor/GSC/사용자 경험 위험을 만든다.

삭제를 허용하려면 최소 조건이 필요하다.

- 실회원 댓글/반응 없음
- 검색 유입 없음 또는 극히 낮음
- 원문 복사/광고/빈 글 위험이 높음
- 대체 URL 또는 대표 페이지 전략이 있음
- 삭제 후 sitemap/cache/revalidate 처리 계획이 있음

## 21. 로그인 Rescue 기준

로그인은 P0다.
로그인이 안 되면 커뮤니티 회복도, North Star도 없다.

로그인 문제는 다음 순서로 분리한다.

| 단계 | 확인 |
|---|---|
| 1 | production `/api/health/auth` 응답 |
| 2 | `/api/auth/csrf` 200 |
| 3 | `/api/auth/providers` 200 및 Kakao provider 존재 |
| 4 | `/login` 화면 렌더 |
| 5 | Kakao authorize URL의 `client_id` 존재 |
| 6 | Kakao callback URL이 운영 도메인과 일치 |
| 7 | OAuth 후 session 생성 |
| 8 | 신규 유저 User row 생성 또는 기존 유저 조회 |
| 9 | 온보딩 필요 여부 판정 |
| 10 | 글쓰기/댓글 진입 가능 |

금지:

- env 값을 보고서에 출력하지 않는다.
- Kakao 앱 설정을 추측하지 않는다.
- auth 수정과 DB schema 수정을 한 PR에 섞지 않는다.
- 로그인 복구 전 UI 리팩토링을 대규모로 하지 않는다.

PASS 기준:

- 비로그인 사용자가 `/login`에서 Kakao 로그인으로 진입할 수 있다.
- 로그인 후 `/my` 또는 원래 callbackUrl로 돌아온다.
- `auth()`가 서버 컴포넌트와 API route에서 같은 user id를 본다.
- 로그인 회원이 글쓰기와 댓글 경로에 진입할 수 있다.

### 2026-09-05 P0 어드민 접근 장애

증상:

- production `/admin/login`에서 `ECIRCUITBREAKER` 또는 DB 인증 실패 계열 메시지가 노출된다.
- production `/api/health`가 DB error를 반환한다.

현재 판정:

- 어드민 비밀번호 불일치 문제가 아니라 production DB 접속 정보 문제로 본다.
- 우선 복구 대상은 `DATABASE_URL`/`DIRECT_URL`/Supabase DB password/Vercel project 연결이다.
- `/api/health/auth`가 캐시되면 운영 판단을 오도하므로 dynamic/no-store 상태여야 한다.

복구 PASS 기준:

- production `/api/health`가 200을 반환한다.
- production `/api/health/auth`가 `x-vercel-cache: PRERENDER` 없이 최신 `ts`를 반환한다.
- `/admin/login`에서 내부 DB 에러 원문이 노출되지 않는다.
- `admin@age-doesnt-matter.com`으로 로그인 후 `/admin`에 진입한다.

Claude 또는 운영자가 할 일:

1. 올바른 Vercel account/team/project에서 age-doesnt-matter production env를 확인한다.
2. Supabase의 현재 DB password와 Vercel `DATABASE_URL`, `DIRECT_URL`을 대조한다.
3. production runtime은 Supabase pooler URL을 우선 사용한다.
4. env 수정 후 production redeploy를 실행한다.
5. 위 PASS 기준을 curl과 실제 브라우저로 확인한다.

## 22. 자동화 출혈 차단

자동화는 Rescue Mode에서 기본적으로 의심 대상이다.

판정 순서:

1. 문서상 ACTIVE인지 본다.
2. `.github/workflows`에 실제 스케줄이 있는지 본다.
3. `.env.local`에서 ON/OFF 값이 있는지 본다. 값은 출력하지 않는다.
4. `launchd`에 실제 plist가 있는지 본다.
5. 최근 BotLog 또는 실행 로그가 있는지 본다.
6. 이 자동화가 로그인, 네이버 신뢰, 콘텐츠 신뢰, 운영 관측 중 무엇에 기여하는지 적는다.
7. KEEP/OFF/REMOVE/OBSERVE로 판정한다.

OFF 우선 후보:

- 외부글 대량 발행 경로
- 봇 댓글 대량 생성 경로
- popular crawler처럼 성공 로그는 있으나 산출물이 없는 경로
- 출처/복사/저품질 위험을 만드는 scraper
- 비용 또는 ISR 폭증을 유발하는 prewarm/revalidate 경로

주의:

- OFF는 삭제가 아니다.
- 삭제는 로그, 호출부, workflow, feature registry, runbook까지 맞춘 뒤 한다.
- "사망 판정" 자동화는 코드 제거보다 먼저 재가동 방지선을 둔다.

## 24. 변경 중단선과 rollback 기준

작업 중 아래가 발생하면 즉시 중단하고 Codex 마스터가 재판정한다.

| 중단 신호 | 이유 |
|---|---|
| 로그인 성공률 악화 | 커뮤니티 생명 기능 훼손 |
| 홈/대표 URL 500 또는 redirect loop | 검색/사용자 모두 치명적 |
| sitemap URL 대량 감소가 의도와 다름 | 색인 신호 훼손 |
| USER/ADMIN 글이 noindex/삭제 후보에 대량 포함 | 사용자 자산 훼손 |
| workflow가 의도치 않게 발행 재개 | 저품질 누적 |
| 소란소란 경로 접근/수정 발견 | 서비스 분리 원칙 위반 |
| DB write 발생 | read-only 감사 원칙 위반 |

rollback 준비 없이 하지 않는 작업:

- SEO 노출면 변경
- 콘텐츠 대량 숨김/삭제
- auth/session 구조 변경
- workflow/launchd 제거
- Prisma schema 변경
