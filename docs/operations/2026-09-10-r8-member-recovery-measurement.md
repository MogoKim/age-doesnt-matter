# R8 회원 소생 측정 — AS-IS 대조와 측정 정의 (2026-09-10)

> 목적: 실회원이 **① 가입 ② 첫 작성 ③ 답글 ④ 재방문** 중 어디서 끊기는지 어드민에서 본다.
> 화면 `/admin/member-recovery` · 쿼리 `src/lib/queries/admin/admin.member-recovery.ts`
> ⚠️ 이 배치는 **측정만** 한다. 가짜 댓글·좋아요·회원 행세 자동화는 만들지 않았다.

## 1. AS-IS 전수 대조 — 이미 있는 것은 다시 만들지 않았다

| 구간 | 기존 자산 | 판정 | 이번 조치 |
|---|---|---|---|
| 방문 세션·채널별 가입 | `admin.insights.ts` `channels` | 채널별 가입률만 있고 **단계 연결이 없다** | 퍼널로 연결 |
| 가입 후 활동 | `admin.insights.ts` `activation` | `User.postCount > 0` **누적 스냅샷** — 코호트·기간·소요시간 없음 | 가입일 코호트로 재정의 |
| 회원 D1~D30 재방문 | `admin.retention.ts` `getRetentionQuadrants()` | **이미 구현돼 있다**(가입 코호트 · `providerId` 숫자 · `role≠ADMIN` · 성숙 코호트 분모) | **재구현 안 함 — 호출해서 붙임** |
| 댓글 → 다른 실회원 답글 | 없음 | 신규 | 구현 |
| 일일 KPI | `DailyKpiSnapshot` | `retention` JSON 은 **비회원 EventLog 기준** | 섞지 않음 |

### 이벤트 계측 현황 (전수)

| 단계 | 이벤트 | 상태 |
|---|---|---|
| 방문 | `page_view` | ✅ 수집 |
| 가입 유도 노출 | `signup_banner_shown` | ✅ 수집 |
| 카카오 로그인 시작 | `kakao_button_click`(공용 CTA 버튼·로그인 화면) ∪ `signup_banner_clicked{cta_type:'kakao_oauth'}` | ⚠️ **부분** — 아래 §3 |
| 가입 완료 | `sign_up` + `User.createdAt` | ✅ 수집(교차 검증) |

## 2. 판정 기준 (전 구간 공통)

- **실회원** = `providerId` 가 순수 숫자(`^\d+$`, 카카오 user ID) **AND** `role !== 'ADMIN'`
  접두어(`bot-`·`seed`·`curator-`) 목록 방식은 7건 어긋난다 — 숫자 판정이 SSoT다.
- 이벤트는 `isBot = false` 만 센다.
- **내부 세션 제외**: `/admin` 경로를 본 세션 또는 `botType='founder'`. 어드민 계정도 분모·분자 양쪽에서 뺀다.
- **분모와 분자를 항상 함께 표시**한다. 비율만 있는 칸은 만들지 않는다.
- **성숙하지 않은 대상은 분모에서 뺀다** — 가입 24h 미경과자, 작성 24h 미경과 댓글. 이들은 "안 했다"가 아니라 "판정할 시간이 없었다"라서 별도 칸으로 보여준다.
- **분모가 0이면 `rate = null`(판정 불가)** 로 두고 화면에도 "판정 불가"로 그린다. **0% 로 그리지 않는다.**

## 3. 알려진 계측 한계 — 숫자보다 먼저 읽는다

| 키 | 등급 | 내용 |
|---|---|---|
| `login_start_rate_limit` | WARN | `kakao_button_click` 이 `api/events` 의 rate limit 면제 목록(`CONVERSION_EVENTS`)에 **없다**. `page_view` 와 같은 버킷(`event:ip`, max 30)이라 429 로 조용히 유실될 수 있다 → **로그인 시작은 하한값**이다. 화면에 `≥` 로 표시한다. |
| `oauth_session_split` | WARN | 카카오 OAuth 는 외부 도메인을 왕복한다. 복귀 시 세션 식별자가 바뀌면 "로그인 시작 → 가입 완료"가 같은 세션으로 안 이어져 전환율이 **실제보다 낮게** 나온다. |
| `signup_cross_check` | OK/GAP | 창 안 `sign_up` 이벤트 세션 수와 `User.createdAt` 기준 신규 실회원 수를 나란히 둔다. 이벤트가 0인데 실제 가입자가 있으면 **GAP** 으로 올리고 "0% 로 읽지 마라"라고 적는다. |

이 한계는 **이번 배치에서 고치지 않았다.** 계측 코드를 바꾸면 측정 대상 자체가 바뀌어 이전 데이터와 비교가 끊긴다.
`CONVERSION_EVENTS` 에 `kakao_button_click` 을 넣는 것은 별도 판단 대상이다(§6).

## 4. 4단계를 다시 계산하지 않은 이유

`admin.retention.ts` 는 **90일 창**을 쓴다. D7 은 가입 후 7일이 지나야 판정할 수 있어서,
7일 창에서 D7 을 재면 성숙 코호트가 거의 0이 되고 **분모 0이 "재방문 0%"로 오독**된다.
그래서 이 화면의 7·30일 토글은 **1~3단계에만** 적용하고, 4단계는 기존 지표를 출처·창 길이와 함께 그대로 싣는다.

**비회원 리텐션은 이 화면에 싣지 않는다.** 같은 함수가 돌려주지만 코호트 정의가 다르다
(비회원 = 첫 `page_view` 일 기준). 섞으면 "회원 재방문"으로 오독된다. 회귀 테스트로 고정했다.

## 5. 개인정보

화면과 쿼리는 **건수·비율·상태만** 다룬다. 닉네임·본문·댓글·`providerId`·IP 를 조회하지도 출력하지도 않는다.

## 6. production 실측 기준선 (2026-09-10 · **2차 보정판**, read-only)

> 🔴 **1차·초판 수치를 모두 철회한다.** 초판은 `page_view` 행 수를 "세션"이라 불렀고,
> 1차는 **정렬 없는 Range 페이징**으로 데이터를 가져와 중복이 섞였다.
> 아래는 **keyset 페이징(`order=id.asc` + `id=gt.<cursor>`) + exact count 대조**로 무결성을 확인한 값이다
> (EventLog 4,188행 · 가져온 수 = 고유 수 = exact count).

단위는 **방문자**(`_anon_sid`, 30일 쿠키). 전환은 **시간 순서**로 검증했다.

| 단계 | 최근 7일 | 최근 30일 |
|---|---:|---:|
| 비회원 방문자 | **206** | **970** |
| 가입 유도 적격 | 12 | 101 |
| 가입 유도 노출 | 12 | 148 |
| 카카오 로그인 시작 | 3 | 15 |
| 가입 완료(이벤트, 방문자 단위) | 0 | 3 |
| **실제 신규 실회원** | **0** | **3** |

| 순서 검증 전환 | 최근 7일 | 최근 30일 |
|---|---|---|
| 비회원 방문 → 적격 | 12 / 206 · 5.8% | 92 / 970 · **9.5%** |
| 적격 → 노출 | 5 / 12 · 41.7% | 57 / 101 · **56.4%** |
| **노출 → 로그인 시작** | 0 / 12 · **0%** | 4 / 148 · **2.7%** |
| 로그인 시작 → 가입(이벤트) | 0 / 3 · 0% | 1 / 15 · 6.7% |

### 1차 → 2차 차이 (무엇이 왜 바뀌었나)

| 항목 (30일) | 1차 | **2차(검증본)** | 원인 |
|---|---:|---:|---|
| 비회원 방문자 | 1,011 | **970** | 정렬 없는 페이징의 중복 제거 + 소급 귀속 반영(+1) + 기존 회원 15명 제외 |
| 가입 유도 적격 | 104 | **101** | 페이징 중복 제거 |
| 가입 유도 노출 | 152 | **148** | 페이징 중복 제거 |
| 방문 → 적격 | 94/1,011 · 9.3% | **92/970 · 9.5%** | 분모·분자 동시 보정 |
| 적격 → 노출 | 57/104 · 54.8% | **57/101 · 56.4%** | 분모 보정 |
| 노출 → 로그인 | 4/152 · 2.6% | **4/148 · 2.7%** | 분모 보정 |
| 수집 완전성 | 건수 3/3 (근거 부족) | **ID 대조 3/3** | 아래 참조 |

### 소급 귀속 반영의 효과
`onboarding.ts` 가 가입 시 과거 익명 이벤트에 `userId` 를 소급 입력하므로, `userId IS NULL` 만으로는
**가입 성공자의 가입 전 방문이 분모에서 빠진다.** 이벤트 시각 < 계정 `createdAt` 이면 "가입 전 방문"으로 보고 되살렸다.
현재 표본에서는 30일 **+1명**(7일 0명)으로 작지만, 가입자가 늘수록 **전환 성공자만 분모에서 사라지는 편향**이 커진다.
같은 판정으로 기존 회원의 가입 후 방문 **15명(7일 5명)** 은 분모에서 제외했다.

### 순서 비교를 `_min` 끼리 하면 놓치는 것
앞 단계의 **최초**와 뒤 단계의 **최종**을 비교한다. `_min` 끼리만 비교하면
"배너를 한 번 본 뒤 적격이 되고 **또 본**" 방문자가 미전환으로 빠진다.
현재 표본 차이는 30일 「적격→노출」 **57 vs 56**(1건)으로 작지만, 재노출이 잦아지면 커진다.

### 가입 수집 완전성 — **ID 대조로 확인**
건수 비교가 아니라 **회원 ID 대조**다(`sign_up` 이벤트의 `userId` ∩ 코호트 ID).

| 창 | 실제 신규 실회원 | ID 로 연결된 회원 | 연결 안 된 회원 | 연결 불가 이벤트 | 완전성 |
|---|---:|---:|---:|---:|---:|
| 7일 | 0 | 0 | 0 | 0 | 판정 불가(분모 0) |
| 30일 | 3 | **3** | 0 | 0 | **100%** |

30일은 **세 명 전부 자기 `userId` 가 붙은 `sign_up` 이벤트를 갖고 있어** 100% 다 — 건수가 우연히 맞은 것이 아니다.
7일은 신규 가입이 0이라 **분모가 없어 판정 불가**다(0% 가 아니다).

### 현재 병목 (2차 수치 기준)
**「가입 유도 노출 → 카카오 로그인 시작」이다** — 30일 **148명이 배너를 봤고 4명(2.7%)** 만 로그인을 시작했다. 7일은 **0 / 12**.
그 앞의 **「방문 → 적격」도 9.5%** 로 좁다(배너를 띄울 조건 자체가 잘 안 맞는다).
가입 단계는 표본 3명 · 수집 완전성 100% 라 **문제로 볼 근거가 없다.**

⚠️ 로그인 시작은 `kakao_button_click` 의 rate limit 유실 가능성 때문에 여전히 **하한값**이다(§3).

## 6-B. 공유 지표 보정 — `admin.retention.ts` 에 `isBot=false` 추가

회원 리텐션은 `EventLog` 의 `page_view`·`login` 으로 "그 날 활동했다"를 판정하는데,
**회원 id 가 붙었지만 봇으로 표시된 이벤트**(`botType='e2e-test'`·`'founder'` 등)에 필터가 없었다.
그대로 두면 그 날짜가 활성으로 잡혀 **D1·D7 이 실제보다 높게** 나온다. 비회원 쪽은 이미 걸러지고 있었다.

- `where` 에 `isBot: false` 추가, 캐시 키를 `v3 → v4` 로 올려 옛 값이 그대로 나오지 않게 했다.
- 이 지표는 **R8 화면이 그대로 재사용**하므로 여기가 틀리면 두 화면이 함께 틀린다.
  회귀 테스트 `src/__tests__/retention-bot-exclusion.test.ts` 로 고정했다(필터 존재 + 동작 + 어드민 제외).

## 7. 후속 (이번 PR 범위 아님)

1. **어드민 첫 화면 링크** — `/admin` 진입 화면에 `/admin/member-recovery` 링크 추가. 그 파일은 다른 작업 흔적이 있어 이번 PR 에서 건드리지 않았다.
2. **`kakao_button_click` rate limit 면제** — 넣으면 로그인 시작이 하한값에서 실측값이 된다. 다만 계측 변경이라 **이전 기간과 비교가 끊긴다.** 적용 시점을 문서에 남기고 그 전후를 나눠 읽어야 한다.
3. **`docs/features/REGISTRY.md` 등록** — 레지스트리는 2026-05-14 이후 갱신이 멈췄고 "수동으로 편집하지 마라" 배너가 붙어 있다. R4/R5 재작성 때 이 기능을 함께 넣는다.
